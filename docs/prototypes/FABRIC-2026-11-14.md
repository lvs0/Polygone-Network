**Périmètre de la tranche** : placement local/distant fondé sur un coût,
consentement local/global, exécution distante sur TCP avec résultat signé
ML-DSA-65, reprise après échec, apprentissage local, et plan de réplication de
blocs adressés par contenu — explicitement **hors Babel**.

**Ce qui est prouvé** : deux processus réels échangent une tâche sur TCP
loopback, le résultat est signé et vérifié, et un résultat altéré ou un nœud
défaillant ne produit jamais un succès. **Ce qui n'est pas prouvé** : un réseau
entre deux machines physiques, le chiffrement de transport, l'authentification
de la demande, l'isolation OS, la découverte mesh, l'intégration au daemon, et
Babel.

## 3. Architecture consolidée de la tranche

```text
TaskSpec (core::task)
  └─ TaskEnvelope { v, scope, global_consent, fabric, requester, task }
       └─ FabricEngine
            ├─ planner::plan
            │    ├─ coût local = file + exécution estimée
            │    ├─ coût distant = transfert A/R + exécution + 2×RTT
            │    ├─ filtre scope / consentement / ressources / échéance
            │    └─ marge : distant seulement si < 90 % du coût local
            ├─ Transport (trait)
            │    ├─ MemoryTransport (tests, démo)
            │    └─ TcpTransport (NDJSON, une requête par connexion)
            │         └─ ServerNode::authorize → TaskKind::execute
            │              → TaskResult::signed (ML-DSA-65)
            ├─ vérification du résultat (hash, signature, NodeId, task_id)
            └─ LearningStore (EWMA local, proposition collective gardée)
```

### 3.1 Contrats

| Contrat | Champs / opérations | Invariant |
|---|---|---|
| `NodeCapabilities` | `node_id`, `scope`, `global_consent`, `local_fabric`, CPU/RAM/stockage/VRAM **offerts**, `load_permille`, batterie/température optionnelles, `user_active`, RTT, débit, taux d'échec, `available` | Une valeur absente reste `None` ; une valeur hors bornes est refusée, jamais corrigée. |
| `TaskEnvelope` | `v`, `scope`, `global_consent`, `fabric`, `requester`, `TaskSpec` | `v` doit valoir `1` ; `fabric` non vide et ≤ 64 caractères. `requester` est informatif, non authentifiant. |
| `PlacementPolicy` | marge 900 ‰, 3 tentatives max, file locale 0 ms | La marge exige que le distant soit au moins 10 % moins cher. |
| `Placement` / `PlacementPlan` | `Local`, `Remote { node }`, `Refused { code, message }` ; estimations et raison | Le plan est sérialisable et lisible par une UI sans recalcul. |
| `Transport` | `list_nodes()`, `dispatch(node, envelope) -> TaskResult` | Le transport rend le résultat **brut** ; seul le moteur le promeut en succès après vérification. |
| Fil TCP | NDJSON : `capabilities`, `run` ; réponses `capabilities`, `ok`, `error` | 2 Mio max par ligne, timeout d'E/S 5 s, 32 connexions simultanées, une requête par connexion. |
| `store` | `BlockId` BLAKE3-256, blocs ≤ 1 Mio, `ContentManifest`, `replica_plan`, `reconstruct` | Chaque bloc est vérifié avant concaténation ; la racine du manifeste est contrôlée. Ce n'est pas Babel. |

### 3.2 Règles de décision effectivement codées

1. **Local d'abord** : une tâche ne part à distance que si le coût distant
   estimé est strictement inférieur à `local_total × 900 / 1000`.
2. **Périmètre** : `Local` exige le même `local_fabric` ; `Global` exige
   `global_consent` côté demande **et** côté nœud **distant**. Une demande
   globale peut s'exécuter sur la machine du demandeur : elle ne publie alors
   aucune ressource. Aucun partage global par défaut.
3. **Priorité utilisateur** : un nœud refuse une tâche distante si
   `user_active`, batterie < 20 %, température > 85 °C, charge > 950 ‰ ou
   ressources insuffisantes. Une demande locale de l'utilisateur n'est pas
   bloquée par `user_active`.
4. **Vérification** : hash BLAKE3, signature ML-DSA-65, `NodeId` dérivé de la
   clé, `task_id` et producteur. Un échec n'est jamais converti en succès.
5. **Reprise** : le nœud fautif est exclu et le plan est recalculé, dans la
   limite de `min(task.max_attempts, policy.max_attempts)`. Une erreur locale
   déterministe n'est pas réessayée.
6. **Stockage** : le hash prouve l'intégrité des octets, pas leur vérité, leur
   disponibilité ou leur confidentialité.

## 8. Installation et lancement

Prérequis : Rust 1.98+ (édition 2024), Linux/macOS/Windows pour la compilation.

```bash
cd ~/Polygone-canonical
cargo build --release -p polygone-fabric --features lab
# Le binaire n'existe pas sans `--features lab` : c'est un laboratoire.

# 1. Démonstration sans réseau (placement + résultat signé + réplication)
./target/release/polygone-fabric demo

# 2. Nœud serveur sur loopback
./target/release/polygone-fabric serve \
  --bind 127.0.0.1:7650 --fabric maison \
  --cpu 8 --ram-mb 8192 --load 20

# 3. Client : charge locale 980 ‰ pour forcer le placement distant
./target/release/polygone-fabric run \
  --peer 127.0.0.1:7650 --fabric maison \
  --cpu 1 --ram-mb 512 --load 980 \
  --kind blake3 --input "portee reelle entre deux processus"
```

Le client imprime un `ExecutionOutcome` JSON. Il sort avec le code **0** si
`verified: true`, **2** sinon.

Pour un essai LAN réel (réseau de confiance uniquement, car il n'y a ni TLS ni
authentification de la demande) :

```bash
# sur la machine serveur
./target/release/polygone-fabric serve --bind 0.0.0.0:7650 --fabric maison \
  --cpu 8 --ram-mb 8192

# sur la machine cliente
./target/release/polygone-fabric run --peer <IP_SERVEUR>:7650 --fabric maison \
  --cpu 1 --ram-mb 512 --load 980 --kind blake3 --input "test"
```

Le port doit être autorisé dans le pare-feu. Ne pas exposer ce prototype sur

## 10. Limites techniques et fonctionnelles

1. **Aucun test entre deux machines physiques.** Le test TCP est un loopback
   entre deux processus, ce que `VISION.md` §4 interdit de présenter comme une
   preuve réseau.
2. **Aucun TLS, aucune authentification mutuelle.** Le canal est lisible et la
   demande n'est pas signée.
3. **Aucune protection anti-rejeu** ni nonce de session.
4. **Aucune isolation OS** : le serveur exécute les tâches dans son propre
   processus. La sandbox systemd/WASM existante de `compute` n'est pas réutilisée.
5. **Aucune découverte automatique** : les pairs sont des adresses explicites ;
   le mesh LAN existant n'est pas câblé.
6. **Aucune intégration au daemon** : les capacités sont déclarées par la CLI,
   pas mesurées par `GlowUpEngine`.
7. **Aucune persistance de l'apprentissage** : l'EWMA est perdue à l'arrêt.
8. **Aucune diffusion des propositions collectives** : la vérification à deux
   est un point de contrôle local, pas un protocole réseau.
9. **Babel non implémenté** : `store` est un CAS expérimental. Aucune
   revendication de compression, de stockage infini ou de recherche exhaustive.
10. **Plan de réplication seulement** : aucun bloc n'est réellement placé,
    répliqué ou récupéré sur des nœuds distants.
11. **Aucune UI, PWA, mobile, GPU, capteur thermique ou batterie.**
12. **Chevauchement avec `compute`** : deux chemins de calcul existent
    désormais. `polygone-fabric` est un prototype de développement, pas une
    commande produit. Il doit être intégré ou retiré avant toute release.
13. **Un seul produit visible** : `VISION.md` §2 impose un produit `polygone`.
    Le binaire séparé est acceptable pour l'expérience, pas pour la livraison.

## 11. Prochaines étapes prioritaires

1. **Décision produit** : intégrer cette tranche à `polygone compute` (réutiliser
   le transport, le placement et la vérification) ou archiver le crate. Ne pas
   maintenir deux chemins de calcul concurrents.
2. **Deux machines physiques** : rejouer le smoke sur deux hôtes du même LAN,
   avec perte de réseau et redémarrage. Sans cette preuve, aucune promesse LAN.
3. **Sécurité du transport** : TLS 1.3 ou Noise, authentification mutuelle des
   nœuds, signature de la demande, nonce/anti-rejeu, révocation.
4. **Isolation** : exécuter les tâches dans la sandbox existante (systemd scope
   ou wasmi) et appliquer les limites CPU/RAM/disque.
5. **Daemon** : remplacer les capacités déclaratives par les mesures réelles de
   `GlowUpEngine`, et refuser si la mesure est inconnue.
6. **Mesh** : câbler la découverte UDP existante pour alimenter `list_nodes`,
   avec appairage explicite et séparation local/global.
7. **Babel** : ne rien coder avant la décision humaine `DEC-028` ; retrouver les
   sources `user-55/65/88/90/91/92/93` et `vision-long.md`, puis écrire une
   spécification vérifiable ou acter que Babel reste une métaphore.
8. **Apprentissage** : persistance locale chiffrée, protocole de proposition
   collective, quorum et audit.
9. **UI de supervision** : afficher placement, `verified`, latence observée,
   raison du refus et limites ; ne jamais afficher une capacité non mesurée.
10. **Device Reuse / PWA** : rôles (relais, stockage, calcul léger, supervision)
    et prototype PWA read-only, sans promesse d'arrière-plan permanent sur iOS.

## 12. Ce qu'il faut retenir

- La tranche est **réelle** : elle compile, ses 32 tests passent, deux processus
  échangent une tâche TCP et le résultat est vérifié.
- Elle est **étroite** : loopback, pas de TLS, pas de sandbox, pas de daemon, pas
  de mesh, pas de Babel, pas d'UI.
- Elle **préserve** les inventions existantes : `TaskSpec`/`TaskResult` de
  `core`, `NodeId` ML-DSA, séparation local/global, refus de promettre une
  accélération.
- Elle **laisse ouverte** la seule question qui compte pour Babel : ce que le
  terme désigne réellement. Aucune architecture générique n'est présentée comme
  le Babel historique.
